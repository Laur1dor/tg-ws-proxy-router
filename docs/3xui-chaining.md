# Заворачиваем Telegram клиентов VLESS/3x-ui в локальный tgws

Сценарий: у вас VPS с [3x-ui](https://github.com/MHSanaei/3x-ui) (VLESS/Reality/
Hysteria2 и т.п.) для общего VPN, и вы хотите, чтобы Telegram-трафик
подключённых клиентов **дополнительно** заворачивался в tgws на этом же VPS —
чтобы Telegram шёл через Cloudflare-WS с фрагментацией, а весь остальной
трафик клиентов уходил как обычно, напрямую с IP VPS.

tgws при этом **не торчит в интернет** — только слушает `127.0.0.1`, наружу
недоступен, доступен исключительно самому Xray на этом сервере.

---

## 1. Включите SOCKS5-вход tgws на localhost

В конфиге tgws (или панели, пункт **2**):
```yaml
listen:
  socks5:
    enabled: true
    host: 127.0.0.1   # НЕ 0.0.0.0 — наружу выставлять не нужно
    port: 1080
```
Перезапустите tgws. Проверка, что слушает только локально:
```bash
ss -tlnp | grep 1080
# должно быть 127.0.0.1:1080, НЕ 0.0.0.0:1080
```

## 2. Добавьте outbound в Xray

В 3x-ui это делается правкой шаблона Xray (Panel Settings → Xray Configuration,
либо напрямую в БД `xrayTemplateConfig`). Добавьте в `outbounds`:
```json
{
  "tag": "tgws",
  "protocol": "socks",
  "settings": { "servers": [{ "address": "127.0.0.1", "port": 1080 }] }
}
```

## 3. Правило маршрутизации: Telegram → tgws

В `routing.rules` добавьте (порядок важен — до общих/пользовательских правил,
чтобы применялось ко **всем** клиентам, независимо от их персональных
исходящих):
```json
{
  "type": "field",
  "outboundTag": "tgws",
  "ip": [
    "149.154.160.0/20", "149.154.164.0/22", "149.154.172.0/22",
    "91.108.56.0/22", "95.161.64.0/20", "185.76.151.0/24",
    "91.105.192.0/23", "5.28.195.0/24"
  ]
},
{
  "type": "field",
  "outboundTag": "tgws",
  "domain": ["domain:telegram.org", "domain:t.me", "domain:telegram.me",
             "domain:telesco.pe", "domain:tdesktop.com", "domain:telega.one"]
}
```
IP-список — это data/DC-подсети Telegram (см. `DEFAULT_DATA_CIDRS` в
[`proxy/utils.py`](../proxy/utils.py)); их достаточно для сообщений/медиа/ботов.

Перезапустите панель, чтобы Xray перегенерировал конфиг:
```bash
systemctl restart x-ui
```

## 4. Проверка

```bash
# xray access-лог должен показать Telegram-подключения через tgws:
tail -f /var/log/x-ui/access.log | grep tgws

# лог tgws должен показать эти же соединения через cf_ws:
journalctl -u tgws -f
```

---

## Варианты

- **Только конкретным пользователям, а не всем.** Замените блок `ip`/`domain`
  на комбинацию с `user`: добавьте `"user": ["alice", "bob"]` в те же правила —
  тогда в tgws попадёт Telegram только перечисленных клиентов, у остальных он
  пойдёт как обычный `direct`.
- **Полное покрытие вместо CIDR.** Вместо списка IP можно использовать
  `"ip": ["geoip:telegram"]`, если в вашей сборке Xray есть база `geoip:telegram`
  (обновляется отдельно, `x-ui update-all-geofiles`) — тогда не придётся
  вручную поддерживать список подсетей.
- **MTProto наружу параллельно.** Ничто не мешает **одновременно** держать
  прямые MTProto-инбаунды tgws (`1443`/`1444`) открытыми наружу — это
  отдельный, независимый способ подключения для тех, кто не пользуется VLESS
  вообще (просто ссылка `tg://proxy?...` из панели tgws, пункт 1).

## Важно про звонки

tgws SOCKS5 — **только TCP**. Через такую связку поедут сообщения, медиа,
боты — а вот голосовые/видеозвонки (UDP к серверам-рефлекторам) через неё не
пойдут: клиент Telegram шлёт их мимо прокси-настроек в принципе. Для звонков
клиентам придётся полагаться на общий VLESS-туннель как есть (если он
достаёт до рефлекторов) — tgws эту часть не решает.

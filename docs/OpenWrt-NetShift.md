# Интеграция с OpenWRT (podkop / NetShift)

Гайд для тех, у кого Telegram заблокирован/режется провайдером и уже есть
роутер на OpenWRT с [podkop](https://github.com/itdoginfo/podkop) (панель
**NetShift**) — либо только роутер, либо роутер **плюс** свой сервер/мини-ПК/LXC
в той же локальной сети.

Идея: весь Telegram-трафик всех устройств в сети заворачивается роутером на
tgws, который поднят **один раз** на выбранной коробке — и Telegram начинает
работать сразу на всех клиентах, без настройки прокси в каждом отдельно.

---

## Где запускать tgws

- **Есть отдельный сервер/мини-ПК/LXC-контейнер в локалке** — ставьте tgws
  туда (рекомендуется). Он не участвует в остальной сетевой логике роутера,
  под него не нужно ничего выделять на слабом железе роутера.
- **Только роутер** — tgws достаточно лёгкий (чистый Python, без тяжёлых
  зависимостей на пути данных), можно запустить прямо на OpenWRT, если у
  роутера хватает флеша/RAM под python3 + venv. На слабых роутерах (типа
  hAP ac²) при 3+ одновременных клиентах будет упираться в CPU — тогда лучше
  вынести хотя бы на самый простой мини-ПК/SBC в той же сети.

Дальше везде: `<TGWS_IP>` — локальный IP коробки с tgws (например
`192.168.1.100`), `<ROUTER_IP>` — IP роутера (обычно `192.168.1.1`).

---

## Настройка NetShift

1. Секция типа **Proxy** (не VPN).
2. **Тип конфигурации** → URL подключения → впишите
   ```
   socks5://<TGWS_IP>:1080
   ```
   (порт и логин/пароль — как настроено в панели tgws, пункт **2**).
3. **Списки сообщества** → выберите `Telegram` — готовый список доменов/IP
   Telegram от [itdoginfo/allow-domains](https://github.com/itdoginfo/allow-domains).
   Можно дополнительно указать свои домены/подсети в соответствующих полях,
   если каких-то адресов не хватает.
4. Save & Apply.

После этого Telegram на всех клиентах локалки должен заработать без ручной
настройки прокси на каждом устройстве — NetShift перехватывает совпадающий
трафик и заворачивает его на SOCKS5-вход tgws.

---

## ⚠️ Почему нужно включить `skip_front`/`tls_fragment` — иначе будет петля

Это главный подводный камень такой схемы, и без него связка **зависает на
~минуту на каждом подключении** (иногда выглядит как «не работает совсем»).

**Механизм петли:**

```
клиент → NetShift(Telegram-лист) → socks5://<TGWS_IP>:1080 → tgws
   tgws пытается выйти на IP САМОГО Telegram (фронт 149.154.167.220,
   или "direct"-выход на IP дата-центра)
   → этот IP тоже попадает под Telegram-лист NetShift
   → NetShift заворачивает исходящий трафик tgws ОБРАТНО на себя же
   → tgws снова пытается выйти на тот же IP → круг
   → выходит из круга только по таймауту (после чего падает на
     Cloudflare-домены, которые НЕ в Telegram-листе → там всё нормально)
```

Проще говоря: tgws сидит **за тем же редиректом**, который сам и обслуживает,
и если он хоть иногда пытается дозвониться до настоящего Telegram-IP напрямую —
роутер перехватывает этот исходящий пакет точно так же, как перехватывает
входящий от клиента, и заворачивает его обратно в tgws.

**Фикс — в конфиге tgws (или через панель, пункт «Расширенные»):**

```yaml
advanced:
  tls_fragment: true   # уже нужен почти всегда за DPI — попутно решает и это
  skip_front: true      # явно: никогда не набирать Telegram-IP напрямую
```

При включённом любом из этих двух флагов tgws **никогда** не пытается
соединиться напрямую с IP-адресами Telegram (ни через «фронт»
`149.154.167.220`, ни через `direct`-выход на подсети дата-центров/рефлекторов) —
только через Cloudflare-домены. Раз tgws не генерирует исходящий трафик к
Telegram-IP, NetShift просто нечего заворачивать обратно — петля физически не
может собраться, и подключение становится мгновенным.

Проверить, что всё чисто, можно по логу:
```bash
journalctl -u tgws -f
```
Не должно быть повторяющихся попыток к `149.154.16x.x` / `149.154.17x.x` с
одного и того же соединения — только один переход сразу на `cf_ws`.

## Звонки — отдельная нога, тут NetShift не поможет

Голосовые/видеозвонки Telegram используют **UDP** к серверам-рефлекторам и
идут **мимо** SOCKS5-прокси приложения в принципе (это поведение самого
клиента Telegram, не наше). tgws не может их перехватить на уровне SOCKS5 —
это тот случай, где нужен отдельный **зарубежный VPN/VPS-выход на уровне
самого роутера** (WireGuard/AmneziaWG и т.п., на подсети рефлекторов
`91.108.4.0/22` … `91.108.20.0/22`), настроенный в podkop отдельно от
Telegram-SOCKS5-редиректа. tgws в этой части не участвует.
